# Spike 结论：unpdf 文本层提取 vs 免费版 CPU 限制

日期：2026-09-29 ｜ 环境：workerd（vitest-pool-workers 本地），Node 22 / wrangler 4.143
测试：`backend/test/30-spike-unpdf.test.ts`（程序化生成 1/5/30 页 Helvetica 文本 PDF）

## 测量数据

| 页数 | 墙钟耗时（含 PDF 解析 + 全页文本提取） | 备注 |
|---|---|---|
| 1 | ~950–1090 ms | 首次调用包含 pdfjs 引擎初始化（模块加载/编译），一次性成本 |
| 5 | ~3 ms | 引擎初始化后 |
| 30 | ~6–8 ms | 引擎初始化后 |

（多次运行数值稳定在 ±3ms 内。）

## 初步结论

1. **首要成本是 pdfjs 引擎初始化（约 1s 墙钟），而非逐页提取**（30 页仅 ~6ms）。
2. 免费版限制是 **CPU 时间（10ms/请求）** 而非墙钟；本地 workerd 无法精确复现线上 CPU 计量，但 30 页文本 PDF 的提取计算量在个位数毫秒量级，**大概率可以直接落在免费版限制内**。
3. 真实赛题 PDF（含中文 CID 字体、扫描混合页、复杂对象树）计算量会高于本 fixture，且**扫描页无文本层可提取**——扫描页本来就走「前端 PDF.js 渲染 → 视觉模型 OCR」路径，不经 unpdf。

## 对 M3 实施的决策（初步）

- **文本提取继续放在后端（unpdf）**，路径保持 PLAN 原设计。
- 为对冲真实 PDF 变重与冷启动，实施时遵守：
  a. 提取放在 **Workflow 步骤** 中执行，整册一次 `getDocumentProxy`，逐页 `getTextContent`，步骤间传引用；
  b. 若线上实测超限，降级顺序：① 按 1–2 页分拆多个步骤/多次调用 → ② 前端 PDF.js 提取文本层上传（需契约微调）→ ③ Workers Paid（$5/月）。
- 部署到免费计划后须用**真实比赛 PDF** 复测一次（观察 Workers 部署面板 CPU 时间指标），结论回填本文件。
