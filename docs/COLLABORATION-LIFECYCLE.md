# 协作任务闭环

任务工作区围绕一个独立主目标统一维护任务、依赖、分工、提交和验收，不改动系统账户等级。旧任务的 ID、完成状态及历史保留；所有新任务使用统一生命周期，不能用任务编辑接口绕过提交与验收直接标为完成。

## 使用方式

1. 项目负责人在「任务」维护一个主目标，明确任务验收标准、工时和前置依赖；也可请 AI 概括目标并拆解，在预览确认后应用
2. 成员在全局个人资料维护专业、技能与特长、偏好及每周总可用时间。项目团队页仅保留身份、角色与任务负荷。每周时间仅本人可见，不进入模型请求
3. 未分配任务可先到先得认领；负责人可说明理由后分工或调整。AI 根据申报资料、任务工时及当前负载给出建议，不评价人员能力、不排名
4. 执行人提交成果说明和已保存的材料固定版本。之后修改材料不会改变本轮证据
5. 系统和项目 AI 启用时，每轮提交自动发起一次评价；AI 禁用时不发起评价。预算不足或排队失败时，提交仍保留并显示实际原因，负责人可直接人工验收
6. 评价结果分为接受、建议改进、返工。改进/返工后执行人提交新一轮成果，旧轮次、旧标准和反馈保留

### 两个独立设置

项目设置中的两个开关默认均为「AI 建议，负责人确认」，只有项目负责人可修改；与系统普通管理员/超级管理员权限无关。

| 设置 | 负责人确认 | 自动模式 |
| --- | --- | --- |
| 分工 | 拆解与分工建议由负责人预览后应用 | 合法拆解先生成总目标和任务，再另行预占预算、排队一次任务分工；不递归拆解，不抢占已认领任务 |
| 验收 | AI 只记录成果建议，负责人明确决定 | 当前配置、任务、提交、成员与设置仍匹配时，自动应用成果评价；正文证据不足不能自动接受；只有未读附件或引用待核验时，可先行接受并标记“已完成（待人工审核）” |

任务统一为平级任务，不保留父任务分组或父任务整体验收特例。负责人调整已提交任务的执行人必须填写理由，旧提交历史保留并失去当前有效状态，旧 AI 结果不能覆盖新的执行人。

项目主目标独立保存，不作为额外任务参与数量和工时计算。历史任务记录继续保留；原有父子分组关系移除。前置依赖仅作提示，未完成前置任务不会阻止提前认领、提交或人工验收。新主目标与依赖拆分方案始终需要负责人预览确认；自动分工只在确认后继续一次有界任务。

项目要求与评分标准在「评分」中共同编辑，保存后立即生效；只有最新保存版本可以用于新的操作。使用页面自动绑定生效标准，不选择历史版本。材料检查和答辩演练分别记录主目标、标准、成果及回答快照，各轮分数不自动合成最终成绩。演练缺少实际回答或可靠证据时保留反馈并标明无法评分，历史文字总结不补造成绩。

## 评价证据边界

- AI 只处理绑定的不可变材料版本正文；提交说明提供上下文，不能替代成果证据
- 原文按完整内容发送，超过模型输入限制直接失败，不截断后声称已全面检查
- AI 报告使用固定版本 ID 和逐字引文；不存在的版本、伪造引文、未知或重复任务/成员 ID 被拒绝
- 附件、图片、外部链接和引用内容没有被读取。自动验收下，正文证据有效、AI 建议接受且其他校验通过，只有未读附件或引用待核验时，可以先行接受并标记“已完成（待人工审核）”；负责人随后完成核验。缺少正文证据、模型自报其他限制或判断不合格时，仍不能自动接受
- 结构与引文校验不能证明模型语义判断正确。报告不是成绩、能力评定或官方评分；项目原有模拟预审仍是独立功能
- 每轮成果最多自动创建一次评价作业，不提供同轮手动重评。AI 禁用时不创建评价作业，最多二十轮提交。已有作业的派发恢复与供应商瞬时错误退避不会创建第二份评价

## 实现与一致性

增量迁移 `0015_collaboration_lifecycle.sql` 给项目增加独立模式和协作设置版本，给成员增加专业，给任务增加生命周期、标准、预计工时等字段；新增提交轮次和建议表。后续增量迁移 `0043_remove_task_parent.sql` 移除历史父任务字段及其自引用外键，任务记录、提交和依赖继续保留。没有重建/删除 jobs、tasks 或旧表，既有已完成任务不强制回填为待验收。

复用 `agent_run` 作业类型，以 `collaboration.decompose`、`collaboration.assign`、`collaboration.evaluate` 操作字段分发；复用旧分工生成器、AI 配置快照、调用留痕、预算预占、outbox 与 Workflow。拆解/分工使用 textEconomy，评价使用 review。自动拆解后的分工拥有独立预占和确定性作业 ID，失败可见且不撤销已保存任务。

所有自动结果在数据库写入时重新核对当前模式/设置版本、最新启用的模型配置、活跃作业和成员。分工还核对任务版本、空执行人、专业/技能/投入时间与负载快照。提交决定核对当前提交、执行人和标准对应的任务版本。模式变化、认领、新提交、改动或成员退出都不会被旧结果覆盖。

认领是带当前用户、成员身份、空执行人和 revision 的条件更新。负责人决定、模式修改和覆盖操作留有审计；相依更新同一批次使用唯一 mutation token，避免重复执行产生双重任务或历史。通用失败作业重试不接受协作操作，必须从当前业务入口重新校验后请求。

### API

所有路径以 `/api/v1/projects/{projectId}/collaboration` 开头，继承登录和项目成员校验。

- `GET/PATCH /settings`：读取/负责人修改两个独立模式和 expectedRevision
- `GET/POST /tasks`：列表/负责人创建有标准的协作任务
- `PATCH /tasks/{taskId}`：负责人修改当前任务内容、标准或工时（提交/已接受阶段不可直接修改）
- `POST /tasks/{taskId}/claim`：本人原子认领
- `POST /tasks/{taskId}/assign`：负责人带理由分工/调整
- `GET/POST /tasks/{taskId}/submissions`：历史/当前执行人新一轮提交固定版本
- `POST /submissions/{submissionId}/decide`：负责人明确决定并说明理由
- `POST /decompose`、`POST /assign`：负责人发起有界 AI 建议
- `GET /proposals`、`POST /proposals/{proposalId}/apply`：建议历史/负责人确认

权威请求、响应与错误契约在生成的 OpenAPI 中。

## 验证与上线边界

本次模型成功路径均使用本地固定响应，不调用付费真实模型。迁移保留测试在内存 SQLite 中创建既有账户、项目、任务、材料版本、作业/outbox、预算、事件与引用，再逐列比较迁移前后并检查全部外键。

新增后端测试覆盖两开关四组合、当前配置与模式变化、claim 冲突、已认领不被覆盖、旧提交/执行人失效、跨项目材料拒绝、完整正文超限、伪造证据、未读附件、父目标人工验收、有界修复与重试、独立预算的自动拆解/分工。

任务和建议沿用游标分页，界面加载全部分页，不会因旧任务超出固定上限而隐藏。编辑、分工、提交、验收与模式表单固定其开始时的版本；后台刷新或冲突不会偷偷提高旧草稿的 expectedRevision，必须明确重载/核对后再提交。切换项目会清空旧项目草稿和轮询。

前端交互测试覆盖 owner/member 控件、手动流程、固定版本与历史、深链接关闭/返回、模式说明与异步结果。`scripts/verify-collaboration-ui.cjs` 是 loopback-only 浏览器 fixture；当前云环境 Chromium 启动遇到 socket EPERM，云浏览器访问 loopback 被客户端阻止，未声称视觉浏览器通过。真实模型表现及人工完整成果复核不由 fixture 测试替代。
